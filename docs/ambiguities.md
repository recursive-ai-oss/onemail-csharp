# Ambiguity table (version 1)

Real mail is full of messages that the RFCs call invalid or leave open, and the established libraries each pick their own
answer. OneMail picks **one documented answer per case**, reports it as a typed defect, and keeps the original bytes so
nothing is lost whichever answer a caller prefers. This file lists each case, what three released libraries do with it, and
the resolution OneMail takes.

## How the table was made

- Each case is a small invented message in [`testdata/differential`](../testdata/differential) (generated by
  [`tools/corpus/make_differential.py`](../tools/corpus/make_differential.py); `cases.tsv` there describes every file).
- Each message was run through MimeKit 4.18.2, Python 3.13 `email` (`policy.default`, `message_from_bytes`) and Go 1.26
  `net/mail` + `mime/multipart`, through the drivers in [`tools/oracles`](../tools/oracles). The columns below are what
  those runs showed. Where the three agree, OneMail does the same.
- Where they differ, the rule is: prefer the answer two of the three give; otherwise prefer the answer that loses no
  bytes and follows the RFC text most closely. No mail client has been observed for any entry yet, so **every resolution
  that is not "all three agree" is provisional**: it is a default, to be revisited when a client's behaviour is observed.
  Provisional entries are marked *prov.*
- "Defect" is the typed defect the parser raises; every repair and every guess carries the byte offset. Names are the
  intended catalogue names; `Ambiguous*` marks a choice between valid readings, the others mark a repair.
- Compared forms, normalisation and the difference classes are in [`tools/oracles/README.md`](../tools/oracles/README.md).

Abbreviations: **MK** MimeKit, **Py** Python, **Go** Go standard library.
